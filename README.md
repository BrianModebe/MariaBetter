# UAE Finance Pro Chatbot 

Covers all seven emirates, not just Dubai -- personal/business finance plus
finance-adjacent law (employment, tenancy/real estate, business licensing,
immigration). Out of scope: criminal, family, and civil-litigation law.

Four chatbots live here side by side while this project is being rebuilt
into a UAE-focused RAG assistant (see the roadmap doc for the full plan),
plus a web UI that can talk to any of the three RAG backends:

- **`main.py`** — the original offline TF-IDF matcher. Keyword-matches a
  question against a fixed knowledge base. No API key needed. Kept as-is
  for comparison.
- **`main_rag.py`** — the retrieval-augmented (RAG) chatbot. Retrieves
  relevant knowledge-base passages, then sends them to the Claude API to
  produce a real, conversational answer (citations on request, see
  "Citations" below), plus a working
  compound-interest calculator called automatically when needed. **Requires
  an Anthropic API key.**
- **`main_gemini.py`** — the same RAG pipeline, generated by Google's
  Gemini API instead (`gemini_chatbot.py`). **Requires a `GEMINI_API_KEY`**
  (get one at https://aistudio.google.com/apikey). Verified live end to end
  (plain Q&A with citation, the calculator tool, the chart tool) — see
  "Gemini backend notes" below for two real issues that were found and
  fixed while doing that, including a truncation bug worth knowing about if
  you ever raise `max_output_tokens`.
- **`main_local.py`** — the same RAG pipeline as `main_rag.py`, but
  generation runs on a local model through [Ollama](https://ollama.com)
  instead of a paid API. No key, no per-query cost, fully offline. Slower
  and less reliable at tool calls than the hosted backends, especially
  without a dedicated GPU.
- **`app.py`** — a Flask web UI in the browser, wrapping all three RAG
  backends behind the same chat page with a dropdown to switch between
  them. See "Web UI" below.

## Setup

```bash
pip install -r requirements.txt
```

For the Claude and/or Gemini bots, copy `.env.example` to `.env` and add
your key(s) -- only the one(s) you plan to use are required:

```bash
cp .env.example .env
# then edit .env: ANTHROPIC_API_KEY=sk-ant-...  and/or  GEMINI_API_KEY=...
```

`ANTHROPIC_API_KEY` comes from the Anthropic Console; `GEMINI_API_KEY` from
https://aistudio.google.com/apikey. Never paste a real key into chat with an
assistant, a commit message, or `.env.example` (the template file, meant to
be shared/committed with placeholders) -- only `.env` (gitignored).

For the local bot, [install Ollama](https://ollama.com), pull the base
model, then build `uae-finance-bot` from the included `Modelfile` (llama3.2
with a lower temperature and higher repeat_penalty tuned for this app --
see the Modelfile for why):

```bash
ollama pull llama3.2
ollama create uae-finance-bot -f Modelfile
```

llama3.1's 8B is slower but more reliable at tool calls if you want to try
it instead: `ollama pull llama3.1`, then `python main_local.py llama3.1`
(the web UI always uses `DEFAULT_LOCAL_MODEL` in `app.py` -- edit that to
switch its default).

## Usage

```bash
python main.py         # old TF-IDF bot, no API key needed
python main_rag.py     # RAG bot via Claude API, needs ANTHROPIC_API_KEY
python main_gemini.py  # RAG bot via Gemini API, needs GEMINI_API_KEY
python main_local.py   # RAG bot via local Ollama model, needs Ollama running
```

RAG bot example session:

```
UAE Finance Pro Chatbot (RAG) -- type 'help' for commands, 'quit' to exit.

> what is uae corporate tax?

The UAE's federal Corporate Tax applies to financial years starting on or
after 1 June 2023: 0% on taxable income up to AED 375,000, and 9% above
that.

> what's your source for that?

Federal Decree-Law No. 47 of 2022 on the Taxation of Corporations and
Businesses [tax.gov.ae, as of 2026-09]

> does that apply to my free zone company?

[follow-up answered using conversation history + free-zone knowledge-base entry]

> if I save 2000 aed a month at 6% for 10 years, what do I end up with?

[calls the compound_interest_calculator tool and reports the projection]
```

## Web UI

```bash
python app.py
```

Then open `http://127.0.0.1:5000`. Pick a backend (Claude API, Gemini API,
or local Ollama) from the dropdown; each browser tab gets its own
server-side chat session. Sessions live in memory only and reset if the
server restarts -- fine for local/personal use, not meant for multi-user
production.

**Two views**: `/` opens the SimpleBit merchant dashboard (`static/app.html`,
with mock payments data and an "Ask Maria" slide-over); the original plain
chat page is at `/static/index.html`. A chat-bubble icon in the dashboard
header switches to the plain chat page, and a "Dashboard view" link in that
page's header switches back. The choice is remembered in `localStorage`, so
`/` opens whichever view you used last (and falls back to the dashboard if
storage is blocked).

**Business-action buttons**: nine tools in `tools.py` make the chat show a
button when the user is genuinely trying to do something right now (never for
an informational question that merely mentions money): `show_payment_button`,
`show_invoice_button`, `show_quote_button`, `show_schedule_payments_button`,
`show_chase_payment_button`, `show_refund_button`, `show_talk_to_team_button`,
`show_set_reminder_button` and `show_register_business_button`. The last one
is for starting a UAE company registration (as distinct from
`show_talk_to_team_button`, which is about onboarding as a SimpleBit
merchant). **None of them is connected to a real SimpleBit backend**: the six
money buttons produce a clearly-labelled demo link (`pay.simplebit.co/...`)
copied to the clipboard, and the other three show a "preview only" message,
because there is no payment processor, scheduler or registry behind them.
Each button's result is stashed on the chatbot (`last_*_button`) and sent to
`maria.html` by `/api/chat`. Adding a tenth means a function + schema in
`tools.py`, a `last_*_button` in all three backends, a field in `app.py`'s
response, a renderer in `maria.html`, a paragraph in `prompts.py`, and (for
the local model) a pattern in `local_chatbot.py`'s `_PAYMENT_REQUEST` -- the
local backend only offers tools when a message matches that pattern.

**Gemini backend notes**: verified live (2026-09-28) with a real key --
plain Q&A with citation, the calculator tool, and the chart tool all
produced correct results (the calculator's numbers matched the app's own
math exactly). Two real issues turned up and were fixed:
- `gemini-2.5-flash` (the model this was originally written against) had
  been retired; the API's own error names the replacement. `DEFAULT_MODEL`
  in `gemini_chatbot.py` now defaults to `gemini-3.8-flash`, overridable
  with a `GEMINI_MODEL` env var if Google moves the goalposts again.
- `gemini-3.8-flash` is a "thinking" model: by default it spends part of
  `max_output_tokens` on a hidden reasoning pass before the visible answer.
  With the app's 500-token cap and a full system prompt, that silently
  truncated real answers to a few words (confirmed live: 367 of 500 tokens
  went to thinking on one request). Thinking is now disabled
  (`thinking_budget=0`) since the system prompt already asks for short,
  direct answers and thinking wasn't buying anything here -- if you ever
  raise `max_output_tokens` for longer answers, keep this in mind.
- The free tier enforces at least two separate 429 quotas for this model --
  5 requests/minute and 20 requests/day, confirmed by hitting both during
  testing -- with the same RESOURCE_EXHAUSTED status either way. A 429 or
  503 from Google now surfaces as a plain-English message instead of a raw
  error dict, and distinguishes the two: the per-minute one says roughly
  how long to wait (from the API's own retry delay), the daily one says
  plainly that it won't clear soon (`GeminiUnavailable` in
  `gemini_chatbot.py`). The free tier's daily cap is easy to exhaust just
  by testing -- if the Gemini backend stops working for the rest of the
  day, that's why.
- Not verified live: multi-turn follow-ups (the same request/response
  mechanism as a single turn, and covered by mocked tests in this session,
  but a live follow-up specifically ran into the rate limit before
  finishing).

**Citations**: by default, answers don't end with a `[Source: ...]` or
`[Federal Decree-Law ...]` tag -- just the substance, verified live to stay
that way on both Claude and Gemini. Ask for the source ("what's your
source?", "which law is that?", "cite that") -- up front or as a follow-up
on the last answer -- and it appears, e.g. "Federal Decree-Law No. 8 of 2017
on Value Added Tax [tax.gov.ae, as of 2026-09]". A bare "what's your
source?" carries none of the original topic's words, so on its own it would
often retrieve nothing relevant; `prompts.py`'s `widen_query_for_citation`
folds the previous question back into retrieval so the same knowledge-base
passage (and its `source`/`legal_ref`) comes back into context, in all
three chatbot classes. Verified live against the real Claude API: a plain
answer has no tag, and "what's your source for that?" right after correctly
cites it. This is the model's own citation behavior; two exceptions handled
separately, deliberately unchanged:
- `chart_library.py`'s ready-made charts (local backend, e.g. "chart the
  rent increase cap in Dubai") never had an LLM call to instruct -- the
  citation is now a separate `ChartHit.citation` field, left out of the
  displayed text by default, and a follow-up citation request falls through
  to the model as above (its topic words are still in the previous turn).
- `predictions.py`'s official-forecast lookups (e.g. "what will inflation
  be in 2027?") still always name the source inline ("The Central Bank of
  the UAE forecasts...") -- deliberately, since who made a forecast IS the
  answer's substance; stripping that would make it indistinguishable from
  the model inventing a number, the exact failure this module exists to
  prevent (see "Predictions" below).

**Live prices**: two different mechanisms, chosen per data source's actual
availability rather than one blanket "web search everything" approach:
- Currency exchange rates use `live_rates.py`, which fetches the Central
  Bank of the UAE's own published rate table directly (not a search
  snippet or third-party aggregator), cached in memory for an hour since
  the CBUAE itself only republishes once a business day. Exposed as the
  `get_exchange_rate` tool in `tools.py`, so all three backends (Claude,
  Gemini, local) get it through the existing shared TOOLS/`call_tool`
  mechanism -- verified live on both the Claude and local backends,
  including that the answer always carries the CBUAE's own "last updated"
  timestamp (this is the one case where a citation-style tag appears even
  when the user didn't ask for one -- a rate without its date is
  misleading, not merely undercited).
- Gold prices, DFM/ADX/Nasdaq Dubai share prices, and current real estate
  asking/rental prices have no free official API (checked: DFM/ADX
  coverage from data providers like Twelve Data sits behind a paid plan;
  Dubai Pulse/DLD's open real-estate data is free but needs the user's own
  registered API key and is historical transaction data, not a live
  listing price). For these, the Claude backend only is wired to
  Anthropic's server-side `web_search` tool (`WEB_SEARCH_TOOL` /
  `WEB_SEARCH_ADDENDUM` in `rag_chatbot.py`), capped at 3 searches per
  question. It is scoped narrowly twice over -- the prompt says only for
  a live price the knowledge base can't hold, and in code the tool is only
  offered when the message looks like a live-price question (`_LIVE_PRICE_RE`,
  English and Arabic; once used, it stays on for the rest of that chat).
  The code gate exists because the prompt rule alone wasn't enough: offered
  on every question, Claude sometimes answered from the KB, ran a needless
  search, and answered again, and the duplicate reached the user. It
  doesn't become a
  back door around the KB-first policy above; verified live that a gold
  price question triggers a cited, dated search result, and an
  out-of-scope question ("best banks for a business account in Sharjah")
  still correctly declines instead of searching. Local and Gemini don't
  have this (no search capability / a different, unwired mechanism), so
  gold/stock/property price questions on those backends fall through to
  the normal "I don't have that" handling.

**Voice**: the mic button next to Send lets you ask by voice (click, speak,
and it sends when you stop; click again to stop early), and the "Speak
replies" toggle reads answers aloud (citation tags are skipped, "AED 5,000"
is read as "5,000 dirhams"). It uses the browser's built-in Web Speech API,
so there's no key or server code. Reading aloud works in any modern browser;
the mic needs Chrome, Edge or Safari, and Chrome/Edge transcribe the audio
online, so voice *input* needs internet even with the local Ollama backend.
English only for now.

**Uploading files**: the paperclip button (or drag-and-drop onto the page)
adds PDF, CSV and Excel (.xlsx) files to the current chat -- up to 8 files or
sheets, 20 MB per PDF, 10 MB per CSV or workbook. Files live in server memory for that chat only; "New chat",
switching backend or a server restart drops them, and nothing is written to
disk. (`pip install -r requirements.txt` adds `pypdf` for PDFs and `openpyxl` for Excel.)
- **CSV** (`csv_tools.py`): charts, totals, averages, median, highest/lowest,
  top-N and "by category" breakdowns are computed by code from the real
  numbers, not by the model -- "chart revenue by region", "pie chart of units
  by product", "what is the total revenue?", "top 5 clients by amount",
  "average price by month". Comma, semicolon and tab files, UTF-8 or Windows
  encodings, and values like `AED 1,200` or `(500)` are handled; dates are
  read day-first. Anything the code can't compute ("why did revenue drop in
  March?") goes to the model along with the file's columns, ranges and first
  rows.
- **Excel** (`.xlsx`, `.xlsm`): every visible sheet with a header row and
  data becomes its own table, named `book.xlsx [Sheet]`, and works exactly
  like a CSV -- your question decides which sheet it's about (by the column
  names you use). Title rows above the header are skipped, dates come through
  as dates, percent-formatted cells as the percentage shown (12.5 for 12.5%),
  and formulas are read as the values Excel last calculated. A file written by
  a script may have formulas with no saved result: those cells come out empty
  and the upload message says so (open it in Excel and save). Old `.xls`,
  `.xlsb` and `.ods` files aren't read -- the app tells you to save as `.xlsx`
  or CSV. Macros are never run.
- **PDF** (`documents.py`): the text is split into passages, the ones that
  best match your question go to the model, and answers cite `[file, p.N]`.
  Scanned PDFs (pictures of text) have nothing to extract and are rejected
  with a message -- there is no OCR. Password-protected PDFs are rejected too.
- Text inside a file is treated as data, never as instructions (the prompt
  says so, and it held against a test PDF containing "ignore all previous
  instructions"). With the **Claude backend**, the passages that relate to a
  question are sent to Anthropic; with **Local (Ollama)** nothing leaves your
  computer. The web page shows a note when you upload on the Claude backend.
- Limits to know about: the small local model reads at most a few short
  excerpts of a long PDF per question, so broad questions ("summarize this
  200-page report") get a sample, not the whole document. `python
  test_documents.py` runs the tests.

**Predictions**: three kinds, all computed by code, none by the model:
- *Trend forecasts of an uploaded CSV* (`forecast.py`, `csv_tools.py`):
  "forecast revenue for the next 3 months", "predict sales next year". It
  fits a straight line to the last (up to 60) periods -- monthly, quarterly,
  weekly, daily or yearly, detected from the dates -- and draws actuals, a
  dashed forecast and an 80% prediction range, with the fit quality (R²). It
  needs at least 6 periods, never goes below zero for an all-positive series,
  averages instead of summing for rate/price columns, and says every time
  that it ignores seasonality and one-off events.
- *Savings goals* (`savings_goal.py`): "when will I reach AED 500,000 saving
  1,500 a month at 5%?" and "how much do I need to save each month to reach
  300k in 10 years at 6%?", with an optional starting balance. Same maths as
  the compound-interest calculator; it asks for whatever is missing (say, the
  assumed return) instead of guessing.
- *Official forecasts and things it won't predict* (`predictions.py`):
  "what will inflation be in 2027?" is looked up in a small table of the
  Central Bank's June 2026 forecasts (growth, non-oil growth, inflation, plus
  the IMF debt projection), reported as a forecast with its source. Requests
  to predict interest rates, the dirham peg, property prices, stocks, crypto,
  gold/oil or salaries get a polite "I don't make my own forecasts of that"
  plus the latest real figure. This exists because the 3B model, left alone,
  answered a 2027 inflation question with a GDP forecast and invented a
  "base rate forecast" -- and attributed made-up salary figures to the
  Central Bank. `python test_predictions.py` runs the tests.

**Charts**: the chatbot can call a `render_chart` tool (bar, stacked_bar,
line, pie, or radar -- alongside `compound_interest_calculator`) to
visualize things like savings growth over time, a budget split, or a
comparison across emirates -- see `tools.py` for when to use each type. The
web UI renders these with [Chart.js](https://www.chartjs.org/) inline in
the chat (bar orientation is decided automatically from label count/length,
not left to the model); the CLI backends print a text note instead, since a
terminal can't draw a real chart.

Reliability depends on the backend. Claude calls this correctly. The stock
local Ollama model is inconsistent -- the *same* explicit "chart this"
request can succeed, get skipped, or spiral into a token-repetition loop on
different runs; a 3B model is small enough that more prompting doesn't
fix that, and neither does parameter tuning (`uae-finance-bot`, see
`Modelfile`, only lowers the temperature -- an earlier `repeat_penalty`
tweak was removed because it didn't help). What does help is taking the
"does this question need a tool?" decision away from the model:
`local_chatbot.py` only offers the tools on chart requests and numeric
growth/savings questions (`GATE_TOOLS`; set it to `False` for the old
always-on behavior), so a plain question like "what's the VAT threshold?"
can no longer wander into a bogus chart call. Growth/savings charts ("invest
800 a month at 8% for 6 years, show a line chart") are built by the code
itself: once the calculator has run, `calc_chart.py` draws the chart and
writes the summary from its numbers, so the model only has to get the four
inputs right, and follow-ups like "graph it", "make it a stacked bar chart"
or "now as a pie chart" reuse that calculation without calling the model at
all. Charts of numbers the knowledge base already holds -- corporate-tax
rate, VAT and other tax thresholds, Dubai's rent-increase cap, gratuity days,
notice periods, the 50/30/20 rule, population of all seven emirates (and
splits by region, gender and nationality), GDP growth 2023-2027 and by
sector, inflation, the budget surplus and government debt, PMI, money supply,
oil production, foreign trade (totals, partners, products), banks by emirate,
type and ownership, EIBOR by tenor -- come from a ready-made library
(`chart_library.py` and `chart_specs_stats.py`; about 15 of them are pies,
and a share-of-a-whole chart can be shown as a bar if you ask for one, or a
count as a pie): the code matches the request, draws the chart and
writes a cited summary, again with no model call. Each chart's numbers are
checked against the knowledge-base entry they cite by
`python test_chart_library.py`; to add a chart, add a spec there and a test
line. Any *other* chart request still goes to the model, which is hit-and-miss
(sometimes invented numbers). When it garbles the chart call, the code no
longer just apologizes: if the knowledge base has a closely matching passage
it retries once as plain text, and if not it says it has no data for that
chart (`RETRY_MIN_SCORE` in `local_chatbot.py`). Charts outside the library
need the fine-tune or the Claude backend. The system
prompt also forbids answering about specific named banks/products/fees from
memory -- the 3B model gets those wrong (it once called ADIB "Al Ahli United
Bank"; ADIB is Abu Dhabi Islamic Bank). The code has defensive layers so
a bad local response degrades gracefully instead of looking broken:
`tools.py`'s `call_tool` validates/coerces arguments and never crashes on a
bad call, `local_chatbot.py` salvages the common "leaked JSON in text"
failure when it can, and falls back to a clean apology when it can't.

The thing that can actually change the model's tool-calling judgment is
fine-tuning: `finetune/` has a LoRA kit (training examples built from the
app's real prompts, a Colab notebook that fits a free T4, and
`Modelfile.tuned` to load the result). Start with `finetune/README.md`.
Until you've run it, for reliable charts use the Claude backend.

## Extending it

- **Add UAE content**: create a new `knowledge/<cluster>.json` file
  following the same schema as `income_taxation.json` (topic, question,
  alt, answer, source, legal_ref, as_of) — `knowledge_loader.py` picks up
  any `.json` file in that folder automatically, no code changes needed.
  `legal_ref` is optional: the specific statute/decree/article a fact rests
  on (e.g. `"Federal Decree-Law No. 33 of 2021, Article 9"`), shown to the
  model so it can quote the real legal basis instead of just a source URL.
  Only set it when verified against an official source (uaelegislation.gov.ae,
  the relevant ministry/authority, or a law firm citing the exact
  instrument) — leave it out rather than guess a law or article number.
- **Statistics** (`knowledge/uae_statistics.json`): population by emirate,
  GDP and sectors, inflation, unemployment, the CBUAE base rate, EIBOR, the
  dirham peg, banking-sector size / bank counts / soundness, and Dubai
  property and rental figures. Every number was read from the official
  publisher (FCSC, the Central Bank's statistical bulletin, quarterly review
  and press releases, the Dubai Land Department, the Statistics Centre Abu
  Dhabi, Sharjah's census release) and each answer states its period, so
  the model doesn't present an old figure as current. These decay:
  **EIBOR changes daily, the base rate whenever the Fed moves, the bank
  figures monthly/quarterly, GDP/population yearly.** Refresh an entry by
  reading the new release, updating the answer text, `source` and the
  `as_of` month -- and update the matching chart in `chart_library.py` (its
  test fails if a chart value no longer appears in the entry it cites).
  Emirate-level figures come from each emirate's own statistics centre, use
  different methods and years, and don't sum to the federal estimate;
  the entries say so. Where an emirate has no recent official figure the
  entry says so instead of guessing: Ras Al Khaimah is only "about 0.4
  million" (RAK Media Office; its 2023 census results weren't found), Umm Al
  Quwain only has its 2005 census figure, Ajman its 2017 census, and
  Fujairah's mid-2025 figure comes from Gulf News quoting the Fujairah
  Statistics Centre. The macro entries (growth history and forecasts, oil,
  trade, fiscal position, PMI, money supply) come from the Central Bank's
  Quarterly Economic Review of June 2026 (data cut-off 12 May 2026) and the
  FCSC's 4 August 2026 Q1 GDP release.
- **Free zones & business registration** (`knowledge/business_freezones.json`,
  72 entries; `knowledge/business_registration.json`, 30): researched from
  each authority's own official site, with third-party figures and anything
  that couldn't be confirmed labelled as such in the answer. Free zones cover
  all seven emirates; several "zones" turned out not to license anyone
  themselves (Dubai Textile City, Gold & Diamond Park and Maritime City are
  licensed through JAFZA or DAFZ; Dubai Investment Park and National
  Industries Park are mainland), so those entries say who actually does.
  Registration covers the mainland licensing authority per emirate (Fujairah's
  is the Municipality), legal forms, the foreign-ownership rule, the three
  offshore registries (JAFZA Offshore, RAK ICC, Ajman Offshore), FTA tax
  registration (VAT, corporate tax, excise), and the approvals needed on top
  of a trade licence by sector: healthcare, real estate, financial services,
  education, manufacturing, telecom (TDRA), Civil Defence and food safety.
  These go stale: authorities get renamed (Dubai DED became DET; the SCA became
  the Capital Market Authority on 1 January 2026), fees change, and a few
  answers are explicitly provisional (the local-service-agent rule for civil
  companies is unclear in official sources, and the Fujairah Department of
  Industry and Economy's own site couldn't be loaded). When adding entries,
  check retrieval with `Retriever.retrieve(query, k=3)`: generic words like
  an emirate name or "banks" get outranked by the statistics cluster, and the
  fix is more alt phrases written the way people actually ask.
- **Add a calculator/tool**: add a schema + function to `tools.py`, then
  register it in `TOOL_FUNCTIONS`. Claude will call it automatically when
  relevant (see `compound_interest_calculator` for the pattern).
- **Swap the retriever**: if the knowledge base grows large or TF-IDF
  matching quality plateaus, replace `Retriever` in `retriever.py` with a
  real embeddings + vector store (e.g. `chromadb`) behind the same
  `retrieve()` method — nothing else needs to change.

## Roadmap

The full step-by-step plan (architecture, UAE content clusters, tech stack,
phased build plan, compliance notes) lives in the "UAE Finance Pro
Chatbot — Roadmap" doc built alongside this codebase. Current status:
Phase 0 (cleanup), the web UI (Phase 3 -- `app.py`), and Phase 1's content
clusters are done -- Income & Taxation (federal), Employment, Tenancy & Real
Estate, Banking & Credit, Retirement & Pensions, Investing, Business & Free
Zones, and Immigration & Visas all exist, plus UAE Statistics. Still to
build: Phase 4/5.

Scope is finance plus finance-*adjacent* law (employment, tenancy, business
licensing, immigration) across all seven emirates -- not a general UAE legal
assistant. Criminal, family, and civil-litigation law are intentionally out
of scope: they don't intersect personal/business finance decisions the same
way, and getting them right needs a licensed lawyer, not a RAG chatbot.

## Disclaimer

This chatbot provides general financial and legal education only — it is
not personalized financial, investment, tax, or legal advice. For anything
specific to your situation, consult a licensed financial advisor
(SCA/DFSA-regulated for investment advice), a UAE tax advisor/accountant,
or a licensed UAE lawyer for legal matters. Some content is federal and
applies UAE-wide; other content (e.g. tenancy rules) varies by emirate or
doesn't apply in the DIFC/ADGM free zones — always check which applies to
you.
